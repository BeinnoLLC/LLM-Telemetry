# P3-03 · Move SQL out of f-strings

**Phase:** 3 — Data plane  **Complexity:** 🟢 low  **Estimate:** ⏱ 2h
**Status:** not started

## Problem

`collect_analytics.py` is 39% embedded SQL inside Python string literals —
including the multi-CTE `SESSIONS_SQL` that joins session usage to titles for
the flow graph's chat attribution.

Not an injection risk today: no user input reaches these queries, the values are
parameterised, and the inputs are profile paths from config. The cost is
reviewability — a long analytical query embedded in an f-string cannot be run in
a SQL client, explained, or diffed meaningfully.

## Change

Move each query to a named module-level constant or a `.sql` file loaded at
import. Prefer `.sql` files for the long analytical queries — they can then be
opened directly in a SQL tool and `EXPLAIN`ed against a real database.

Keep parameter binding exactly as it is. This is a readability change, and it
must not become a string-building change.

## Acceptance

- [ ] No multi-line SQL remains inline in `collect_analytics.py`.
- [ ] All queries stay parameterised — no f-string interpolation of values.
- [ ] Payload output is byte-identical before and after (golden fixtures from
      P1-03 prove it).

## Notes

Watch for queries that interpolate *identifiers* (a table or column name) rather
than values — those cannot be parameterised and need an allowlist instead. If
any exist, that is a genuine finding worth calling out separately.
