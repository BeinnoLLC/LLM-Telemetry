# P2-06 · Point the suites at modules, not built HTML

**Phase:** 2 — Presentation  **Complexity:** 🔴 high  **Estimate:** ⏱ 6h
**Status:** not started
**Depends on:** P2-02

## Problem

All 18 suites load the **built** `dashboard.html` into jsdom and inspect the
resulting DOM. That has real value as integration coverage, but it means:

- No function can be tested in isolation — testing `toolColor()` requires
  building and loading an entire page.
- Suites need a Chart.js stub and a CDN strip to run at all.
- Failures point at a rendered page, not at the function that produced it.
- Some assertions have to test the CSS *contract* (rule text) rather than real
  layout, because jsdom does no layout — `check_livegrid.js` does exactly this.

## Change

Once the JS is in modules, let unit-level suites `import` and call functions
directly. Keep a deliberately thin set of integration checks against the built
artifact, so the assembly step stays covered.

Split the intent explicitly:

- **Unit** — palette determinism and ΔE spacing, heat scaling, cost maths,
  `provOf()` classification. Fast, no DOM.
- **Integration** — page boots, tabs switch, drawer opens, charts instantiate.
- **Visual** — the screenshot checks that catch what neither of the above can.
  The glow bug is the case in point: every DOM assertion passed while the effect
  was invisible on screen. Keep this category; it is the only one that would
  have caught it.

## Acceptance

- [ ] Unit suites import modules directly and need no jsdom.
- [ ] Integration suites still cover boot, tabs, drawer, charts.
- [ ] Total coverage does not regress — 237 checks is the floor.
- [ ] Suite runtime improves (currently ~40s; most of it is page builds).

## Notes

Do not delete the DOM-level suites when their unit equivalents land. They cover
different failure modes: a correct function wired to nothing still renders a
broken page, and only the DOM suite sees that.
