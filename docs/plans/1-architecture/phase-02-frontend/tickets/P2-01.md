# P2-01 · Extract CSS to web/css/dashboard.css

**Phase:** 2 — Presentation  **Complexity:** 🟢 low  **Estimate:** ⏱ 3h
**Status:** not started

## Problem

218 CSS rules live inside Python string literals. No stylelint, no editor
support, no diff review that understands what changed. Two shipped bugs came
straight from this blind spot:

- `.olfill` was an `<i>` element with `width:46%` set, rendering **0.0 × 0.0**,
  because `<i>` defaults to `display:inline` and inline elements ignore width
  and height. Every Ollama progress bar was invisible. Found only by injecting
  JS to measure `getBoundingClientRect` — the CSS *looked* right.
- `#flow .nd{cursor:pointer}` silently overrode `.nd{cursor:grab}` on
  specificity, so draggable nodes advertised themselves as clickable.

## Change

Move all CSS into `web/css/dashboard.css`. The build step copies or inlines it.

This is a **pure move**. No renaming, no reordering, no "while I'm here"
cleanups — the diff should be reviewable as a relocation, and any behaviour
change must be a separate commit.

Keep the theme variables working: the page is themed by CSS custom properties
injected by the host frame, so nothing may hardcode a colour that currently
comes from a variable.

## Acceptance

- [ ] Zero CSS rules remain in `build_dashboard.py`.
- [ ] Rendered output is visually identical — verify by screenshot comparison at
      the same viewport, not by reading the diff.
- [ ] The 237 existing checks still pass.
- [ ] Custom-property theming still resolves.

## Notes

Decide deliberately whether the build **inlines** the CSS into a single-file
dashboard or **links** it as a separate asset. Inlining keeps the "one file you
can email or open from disk" property that the sample dashboard relies on;
linking is cleaner but makes the artifact a directory. Inlining at build time
from a real source file gets both — real file for tooling, single file for
shipping. Recommended.
