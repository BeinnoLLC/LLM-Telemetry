# P5-06 · CI must not read the developer's real `~/.hermes`

**Complexity:** 🟡 medium  **Estimate:** ⏱ 3h  **Depends:** P5-01
**Status:** not started

## Problem

Because of P5-01, the sample build ignores `"profiles": []` and autodiscovers
the real agent home. Consequences:

1. **The green build proves nothing.** `render dashboard from committed sample
   data` does not use the committed sample data when a real `~/.hermes` exists.
2. **Privacy.** The leak gate (`examples/check_no_leaks.py`) scans `examples/`,
   so it cannot see data pulled from outside that tree. Locally, real session
   titles and costs land in a build output that a careless `git add` could
   commit.

On CI the runner has no `~/.hermes`, so discovery finds nothing and the build
happens to pass — which is exactly why this has gone unnoticed. The behaviour is
wrong in both environments; only the symptom differs.

## Change

- Land P5-01 so `"profiles": []` is honoured.
- Give the sample build an explicit fixture agent home via the P5-03 env var,
  rather than relying on the absence of a real one.
- Add a CI guard that **fails** if the rendered sample dashboard contains data
  from outside `examples/` — assert against known fixture markers, so the check
  works locally too, where a real home does exist.
- Extend the leak gate to scan the rendered `dashboard.html`, not just the JSON
  payloads.

## Acceptance

- [ ] Sample build is reproducible on a machine that has a populated
      `~/.hermes`, producing identical output to a machine without one.
- [ ] CI fails if the sample dashboard contains non-fixture profile names.
- [ ] Leak gate covers the rendered HTML.
- [ ] Documented: how to render the samples without touching your real data.

## Notes

This is the highest-value ticket in the phase — it is the difference between a
CI suite that verifies the committed fixtures and one that verifies whatever
happens to be on the developer's laptop.
