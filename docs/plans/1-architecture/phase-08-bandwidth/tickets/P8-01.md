# P8-01 · Byte estimator: one function, calibrated, with its assumptions named

**Phase:** 8 — Bandwidth  **Complexity:** 🟡 medium  **Estimate:** ⏱ 4h
**Depends:** —  **Status:** done (`ad578ea`, #74)

## Problem

Bandwidth is not recorded anywhere, but it is derivable from token counts. The
risk is a number that looks authoritative and is quietly wrong, rendered in four
places at once.

## Measured on the live DB before writing this

No byte counters exist anywhere in the schema (only `hosted_rooms.event_bytes`,
unrelated to LLM traffic). `messages.token_count` is **NULL in all 425,427
rows**, so per-message calibration is impossible. Session-level join works:

    269 sessions · 560,471,345 stored body bytes · 121,273,494 in+out tokens
    -> ~4.6 bytes per token (4.68 on the run recorded below)

That lands near the ~4 chars/token rule of thumb, which is why the method is
trustworthy rather than a guess.

**The number that matters.** Splitting prompt tokens:

| | tokens | share |
|---|---:|---:|
| input (fresh) | 104,410,872 | 2.4% |
| cache_read | 4,311,531,663 | **97.6%** |
| output | 16,862,622 | — |

Context is re-sent **42x per unique stored byte**. Bandwidth is almost entirely
re-sent conversation history, not new prompts and not replies.

**Resolved: prefix vs handle-based caching.** This was the one assumption that
could have moved the estimate by 40x, and live data settles it:

    anthropic    cache_read=3,886,077,710  cache_write=243,023,794  calls=26,512
                 -> 146,578 cache_read tokens PER CALL
    opencode-go  87,682 per call, cache_write=0
    custom       13,268 per call, cache_write=0

`cache_write > 0` means the client sent a prefix and asked the server to store
it. 146k read tokens per call is a whole conversation re-sent, not an id. No
provider shows the handle-based signature (high reads, zero writes, tiny
per-call). **Every caching provider re-sends context**, so cache_read tokens
genuinely cross the wire.

**Unresolved: request-body gzip.** Anthropic returns `Vary: Accept-Encoding`,
but that governs *responses* — the tiny half. Whether the client sets
`Content-Encoding: gzip` on *request* bodies cannot be verified here: the Hermes
client source is not on this box. Default httpx/requests do **not** gzip request
bodies, so raw is the likelier figure. Measured on real message content, gzip -6
gives 3.65x.

| | raw | if request gzip is on |
|---|---:|---:|
| Internet upload | 18.74 GB | 5.13 GB |
| Internet download | 0.07 GB | 0.02 GB |
| LAN (local models) | 0.27 GB | — |

Over 31,782 API calls. Upload:download is **278:1** — inverted versus normal web
traffic, because you ship a conversation to receive a paragraph.

## Change

One function in Python, used by every consumer — no second copy in JS:

    bytes_for(input_tokens, output_tokens, cache_read_tokens) -> (up, down)

- `BYTES_PER_TOKEN = 4.68`, defined once, with the calibration query in a
  comment so the next person can re-derive it.
- Upload = `(input + cache_read) * B`. Download = `output * B`.
- Local/LAN traffic is computed but kept in a **separate** bucket. It is not
  internet bandwidth and must never be summed into the billable figure.
- The result carries `estimated: true` and a `basis` string. A consumer that
  cannot say "estimated" must not render it.
