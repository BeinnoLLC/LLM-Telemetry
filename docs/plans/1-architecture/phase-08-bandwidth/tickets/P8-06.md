# P8-06 · Settle request-body gzip, then correct every rendered figure

**Phase:** 8 — Bandwidth  **Complexity:** 🟢 low  **Estimate:** ⏱ 2h
**Depends:** P8-01  **Status:** not started

## Problem

Every figure in this phase is raw bytes. If the HTTP client gzips request
bodies, the true upload is **3.65x smaller** — 18.74 GB becomes 5.13 GB. That is
not a rounding difference, and it is currently unverified: the Hermes client
source is not on the telemetry box, so it could not be read.

What is known:

- Anthropic returns `Vary: Accept-Encoding`, but that governs **responses** —
  the 0.07 GB half, not the 18.74 GB half.
- Default `httpx` / `requests` do **not** gzip request bodies. Raw is therefore
  the likelier figure, which is why it is the default here.
- Measured on real message content, gzip -6 compresses 3.65x.

## Change

Verify once, then make the rendered numbers honest.

1. Read the client's request path; check for `Content-Encoding: gzip` on POST.
2. If absent: keep raw, and state "uncompressed" in the panel footnote.
3. If present: apply the measured 3.65x and label figures "gzip-adjusted".
4. Either way, record the finding in the ADR so it is not re-litigated.

## Acceptance

- [ ] The gzip question is answered from source, not inferred.
- [ ] Rendered figures state which basis they use.
- [ ] The factor lives beside `BYTES_PER_TOKEN`, not scattered.

## Notes

Worth doing early — it is one grep, and it decides whether four views are
showing a number that is 3.65x too high.
