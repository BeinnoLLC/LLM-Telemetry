# P8-04 · Persist bandwidth per day so it can be tracked over time

**Phase:** 8 — Bandwidth  **Complexity:** 🟡 medium  **Estimate:** ⏱ 3h
**Depends:** P8-01  **Status:** not started

## Problem

"Keep tracking" means the number must survive. Today every figure is recomputed
from the DB on each build, so if the estimator's constant changes, history
silently changes with it — last month's bandwidth is restated and nobody knows.

## Change

Write a daily bandwidth rollup into the analytics payload: date, project,
provider, model, up_bytes, down_bytes, lan_bytes, plus the
`bytes_per_token` used.

- Storing the constant alongside the numbers is the point: a later recalibration
  must not rewrite history.
- Feeds the trend chart in P8-05.
- Must carry `schema_version` per P1-01 (#23).

## Acceptance

- [ ] Payload gains a dated bandwidth series, one row per day/model/provider.
- [ ] Each row records the `bytes_per_token` it was computed with.
- [ ] Re-running the collector twice produces identical output.
- [ ] Changing the constant does not alter already-written history.

## Notes

Depends on #23 landing first — adding a payload dimension without a version
field repeats exactly the failure class in ADR 0001.
