# P9-02 · Live row title opens a read-only chat transcript modal

**Phase 9 — Brand, transcript preview, and unused-signal panels** · ticket `P9-02` · complexity 🔴 high · est ⏱ 8h · depends: -

## Problem

A live row tells you a session is running and what phase it is in, but not what
it is actually *doing*. Opening the real chat means finding the session by hand
in another tool.

## Change

Make the title in each "In progress now" row a button that opens a modal showing
that session's conversation, styled like a chat/terminal window, **strictly
read-only**.

## The constraint that decides the design

Measured on the busiest live session (`20260918_210815_84cda7`):

    72,421 messages
    32,035,388 chars  =  30.6 MB  of transcript
    roles: assistant 35,837 · tool 31,537 · user 5,047

**One session is 30.6 MB.** The dashboard is a single self-contained HTML file
(ADR 0001) and `serve.py` is `SimpleHTTPRequestHandler` with no API — so the
transcript cannot be embedded, and there is nothing to fetch it from.

This is a real architectural fork and must be decided before implementation:

- **(a) Windowed payload.** Collector writes the last N messages per live session
  (say 200) to a separate `transcripts.json`. Bounded, works offline, keeps the
  single-file model. Cost: it is a tail, not the whole chat.
- **(b) Real endpoint.** `serve.py` gains `GET /api/session/<id>/messages` with
  paging, reading the DB read-only. Full history, lazy-loaded. Cost: the tool
  stops being a static artifact — contradicts ADR 0001 and needs the
  single-user question (#36) answered first, because an endpoint that serves any
  session id is an access-control surface.
- **(c) Per-session sidecar files.** One JSON per live session, written by the
  poller. No server change, but writes churn and needs GC.

Recommendation: **(a) for this ticket** — it delivers the preview with no
architectural change — and file (b) separately if full history is wanted.

## Requirements

- Title is a real `<button>`, keyboard-focusable, not a clickable `<div>`.
- Modal is read-only: no inputs, no textarea, no contenteditable anywhere.
- Roles visually distinct (user / assistant / tool).
- Renders **content safely**: message text is untrusted input and must never be
  injected as HTML. Escape everything, then opt in to specific affordances.
- Measured content that must render correctly in that one session:
  - `http(s)` links: 2,560 messages
  - fenced code blocks: 662
  - `data:image` URIs: 91
  - `MEDIA:` file paths: 12
  - markdown `![]()` images: 0
  - ANSI escapes: 0
- Long transcripts must not freeze the page: virtualise or cap rendered nodes.
- Esc closes, focus is trapped while open, focus returns to the trigger on close.
- Works at 360px.

## Acceptance

- [ ] Clicking a live row title opens the modal for THAT session.
- [ ] Nothing in the modal is editable (assert zero `input`, `textarea`,
      `[contenteditable]` nodes).
- [ ] A message containing `<script>` or `<img onerror=>` renders as literal text
      — asserted by a test, not by eye.
- [ ] Links are clickable, open in a new tab, and carry
      `rel="noopener noreferrer"`.
- [ ] Code blocks render monospaced and preserve whitespace.
- [ ] `data:image` renders as an image; a broken one degrades to a placeholder,
      not a JS error.
- [ ] Esc closes; focus returns to the title button.
- [ ] Rendering 200 messages does not block the 5s live poll.
- [ ] Modal is scrollable and readable at 360px.

## Notes

`tool_calls` carries ~550 byte JSON payloads with empty `content` — tool
invocations need their own rendering or they appear as blank bubbles.

Do not reuse the existing logs drawer: that is a cross-session tail, this is one
session's full conversation.
