# P9-06 · Concurrency panel: peak parallel sessions and pile-ups

**Phase 9 — Brand, transcript preview, and unused-signal panels** · ticket `P9-06` · complexity 🟢 low · est ⏱ 3h · depends: -

## Finding

    max sessions started in a single hour: 28
    tool_calls=14,393 across messages=28,392 over 292 sessions

28 sessions in one hour, and the dashboard never shows concurrency over time.
The Live view shows what is running *now*; the Usage view shows daily volume.
Neither answers "how many agents were running at once" — which is the question
that matters when the GPU box saturates or the API rate-limits.

## Change

A concurrency band (Usage or Health view):

- Sessions active per hour over the selected range.
- Peak marked with its value and timestamp.
- Overlay of the local-inference queue depth already collected by
  `probe_hosts.py`, so saturation and concurrency are read together.
- Subagents distinguished from top-level sessions: 24 of the sessions here are
  subagents, and counting them as independent work overstates parallelism.

## Acceptance

- [ ] Hourly active-session count rendered for the selected range.
- [ ] Peak labelled with value and time.
- [ ] Subagent vs top-level split visible.
- [ ] Empty range renders an empty state, not a broken axis.
- [ ] Peak matches a direct SQL check on the same window.
