# P1-03 · Golden payload fixtures

**Phase:** 1 — Contract  **Complexity:** 🟡 medium  **Estimate:** ⏱ 3h
**Status:** not started

## Problem

`examples/make_sample_data.py` builds the sample by **reshaping a real payload**
— deterministic pseudonyms over real structure. That design is deliberate and
correct: an earlier hand-written sample invented the schema, got `d` vs `date`
wrong, and rendered zero rows.

The side effect is that the sample's shape tracks whatever the collector
currently emits. If a collector changes shape, the sample changes with it and
the tests keep passing — the regression is invisible precisely because both
sides moved together.

## Change

Freeze a known-good payload as a golden fixture and diff against it in CI.

- Commit `tests/fixtures/golden-analytics-v1.json` (and siblings).
- A CI step regenerates from a fixed input DB and diffs against the golden file.
- A diff fails the build with a readable report of which keys changed.
- Updating a golden file is a deliberate, reviewable commit — that is the point.

Build the fixture input as a small synthetic SQLite database committed to the
repo, so the golden output is reproducible on any machine. Generating it from
the author's live 2.2 GB database is neither reproducible nor publishable.

## Acceptance

- [ ] A small fixture SQLite DB is committed (kilobytes, not megabytes).
- [ ] Golden payloads are committed and regenerate byte-identically from it.
- [ ] CI fails on unreviewed shape drift.
- [ ] The leak gate passes over the new fixtures — they must carry no real chat
      titles, paths, or LAN IPs.

## Notes

Watch determinism: anything carrying a timestamp, a set-iteration order, or a
dict ordering will diff on every run and train everyone to ignore the check.
The tool colour palette already hit exactly this — a live-feed-derived roster
produced 15 tools in one build and 13 in the next — and was fixed with a fixed
roster plus sorted input. Apply the same discipline here.
