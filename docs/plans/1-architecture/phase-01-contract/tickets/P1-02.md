# P1-02 · JSON Schema for the four payloads

**Phase:** 1 — Contract  **Complexity:** 🟡 medium  **Estimate:** ⏱ 4h
**Status:** not started
**Depends on:** P1-01

## Problem

The producer (Python) and the consumer (JavaScript) agree on payload shape only
by coincidence and memory. Nothing checks them against a common definition, so a
rename on either side is caught by a human noticing a blank chart.

## Change

Write JSON Schema for each payload under `src/llm_telemetry/schema/`:

    analytics-v1.json, live-v1.json, ollama-v1.json, router-v1.json

Then assert against it from both directions:

- **Python, at write time** — validate before the file lands. A collector that
  would emit a malformed payload should fail, not write it.
- **Node, in the suites** — validate the fixtures the tests load.

Keep the schemas *forgiving where the data is genuinely optional* and strict
where the consumer will crash. Specifically: remote hosts legitimately omit
CPU/GPU fields (we never invent telemetry for a host that cannot report it), so
those are optional — but `generated` must be a string, because the consumer
calls string methods on it.

Prefer a vendored single-file validator or a stdlib-only check over adding
`jsonschema` as a runtime dependency; the package is stdlib-only today and that
property is worth keeping. A dev-only dependency is acceptable.

## Acceptance

- [ ] Four schema files exist and are versioned in their filename.
- [ ] Python validates each payload before writing it.
- [ ] The Node suites validate the fixtures they load.
- [ ] A deliberately corrupted payload fails both checks — proven with a test
      that corrupts it, not by assertion.
- [ ] Runtime stays stdlib-only (dev-only dependencies are fine).

## Notes

Optionality is the subtle part. Over-strict schemas will reject the honest
"remote host reports no GPU" case and push someone toward inventing zeros —
exactly the behaviour the collectors were written to avoid.
